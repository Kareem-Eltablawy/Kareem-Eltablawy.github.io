⚙ Technical Architecture
⚔ Unreal Engine 5 — Native C++ Systems
▸AI & Combat — Event-Driven C++, No Behavior Trees
Enemy, companion and NPC AI is written entirely in C++, without Behavior Trees. Each brain follows a zero-tick design, so it reacts to events such as overlaps, timers and animation completions instead of checking the world every frame. That covers attacks, dodging, defending and hit reactions, and because NPC types are built through inheritance, a new enemy or companion extends an existing base instead of starting from scratch.
▸Animation — Custom C++ with Smooth Interrupts
Characters run on custom C++ animation systems built around FAnimInstanceProxy, with upper and lower body working as concurrent layers. Transitions use snapshot blending, so when a hit reaction or other interrupt lands, the character blends out of the pose it is actually in and nothing pops. The system stays stable with many characters on screen, and faces run through the MetaHuman pipeline with ControlRig and RigLogic.
▸Living World — Day/Night Cycle & NPC Routines
The world has a day/night cycle, and NPCs follow daily routines of sleeping, eating and idling that are driven by in-game time. This lets the same NPCs feel different at different hours without scripting each scene by hand, and the schedules are tuned through data instead of code.
▸Companions — Player-Led Team
The player leads a companion team and gives it commands, with limits on roster size so the team stays readable and manageable in combat. Companions use the same event-driven C++ approach as enemies, so they stay cheap to run even when several of them are active alongside the player.
▸Data-Driven Design — Tuned in Data Assets
Designers tune values in Data Assets without changing code, using a UPrimaryDataAsset hierarchy for the project's settings. Blueprints are kept to designer-facing configuration while the core systems stay in native C++. Ownership is explicit as well, with TObjectPtr for owned objects and TWeakObjectPtr across actors, which keeps garbage collection predictable.
▸Performance — Event-Driven, LOD & Compact Data
Logic is event-driven rather than ticked, and AI and animation both use distance-based LOD, so characters far from the player are cheap to run. Hot paths use compact data layouts and avoid heap allocation, while actor pooling, overlap-based activation volumes and timer-driven projectile pools keep spawning and activation costs down.
◈ Unity — C# Systems Architecture
▸AI Written from Scratch in C#
Behavior trees, FSMs and utility AI are all written from scratch in C#, which I have used across strategy, simulation and open-world projects. Owning the AI code means decisions are easy to trace and tune, and each system can be built to fit the performance budget of the project instead of adapting to a framework.
▸Data-Driven Design — ScriptableObjects & Backends
ScriptableObjects are the source of truth for game data, fed by JSON from ASP.NET and REST backends. The result is that server data can update game content without code changes or rebuilds, so values can change quickly without waiting for a new build.
▸Event-Driven — Update Only Where It Counts
Update is used only for animation, physics and input, and everything else runs on events. Systems do work when something actually happens, which keeps per-frame cost low and makes behavior easier to follow because each change has a clear trigger.
▸Performance — Streaming, Pooling, LOD & ECS
World streaming, object pooling and AI LOD keep open environments and mobile builds running smoothly. For CPU-heavy simulation I use ECS, the Job System and Burst, so large amounts of work can be spread across cores instead of sitting on the main thread.
